# AgentDock V0.1 Build

Status: V0.1 scope and primary test seam accepted on 2026-11-16. Implementation and runtime verification are tracked separately.
Parent: AgentDock Product & Engineering Specification, document version 0.2.0, §§2.1, 3.1, 4.1–4.2, 5.2 and 5.7.

## Problem statement

A developer using a Coding Agent can build a container without proving that the real application can perform their task through the CLI documented by its Skill. The developer needs a package they can inspect, test and rebuild without manually stitching together those tools.

## Solution

From one task in a supported Codex environment, the Builder Skill produces an Application Sandbox Package and runs a local verifier. The package carries a rebuild recipe, source and tool identities, CLI and Skill provenance, image identity, and validation evidence.

## User stories

1. As a developer, I want to give Codex an application source and a task so that it can build and verify a local package.
2. As a developer, I want a suitable native CLI and matching Skill reused so that upstream guidance stays useful.
3. As a developer, I want a matching Skill generated for my native CLI when one is missing.
4. As a developer, I want CLI-Anything to provide the CLI and Skill together when the app has no suitable CLI.
5. As a maintainer, I want to rebuild the package from pinned inputs and replay validation.
6. As a developer, I want the verifier to reject malformed output even when the application exits successfully.
7. As a developer, I want the build to stop if its requested permissions exceed those of the configured environment.

## Implementation decisions

- V0.1 supports Codex and targets applications that can run noninteractively in Linux containers. E2E and Sand3D are required launch applications. Cursor and Claude Code each have separate post-launch acceptance. The initial Linux container architecture is proposed to match the available runner and is recorded in evidence.
- The Builder Skill prefers a suitable native CLI for each application, reuses a compatible upstream Skill where available, records why, and invokes the local verifier. AgentDock reuses Docker/BuildKit for image construction and the supported CLI-Anything Coding Agent workflow for paired generation.
- Build and run the two reviewed, revision-pinned fixtures through the configured Docker/BuildKit daemon. The host build script stages a Git archive and explicit fixture inputs in a temporary context. The recipes pass no host workspace mounts, credentials, proxy settings, SSH forwarding, or Docker sockets to build steps or runtime containers. Network access is available during dependency retrieval. BuildKit disables networking while building application source and Docker disables networking during fixture execution, with loopback available to the E2E browser target. A required restriction the environment cannot enforce fails the run. Arbitrary external repositories require a separately configured policy.
- The build script writes a host-side receipt with the inspected local image ID, platform, Dockerfile hash, source and tooling provenance. The runner requires the trusted local receipt for the same fixture and image ID. The receipt is a local record and carries no signature. The artifact verifier can run independently and checks only the supplied file.
- The verifier owns the outcome. Fixture expectations live in an independently maintained suite. It records the image identity, Skill identity, verifier and fixture versions, exit status and artifact assertions. Package-authored claims do not confer verification.
- Report a local image ID for a local-only package. The OpenSandbox milestone defines the registry/import handoff by digest and reruns application acceptance on the target.

## Testing decisions

The primary seam is the developer-visible CLI/Skill workflow: application source + task → build → verifier → real file and structured result. Automation invokes the same public verifier command as the Builder Skill. A Codex session provides separate evidence that one request can drive the workflow.

- **E2E**, source revision `783a8c94c67cfe950e62f43ff44e29177345415a`: run a browser check against a controlled local target and assert the expected case passed in `report.json`. Use the upstream `e2e` CLI and compatible upstream Skill. Use deterministic steps with no agent/model dependency in the browser run.
- **Sand3D**, source revision `5cdb54e4aef76377ad1a8bbc11e257eee8fc2341`: use Blender through the upstream `sand3d` Python API to model a bracket and export a GLB. Validate the container format and presence of the expected plate geometry independently. The checkout documents a Python API and declares no application CLI in its package metadata. The entrypoint will be a small CLI and matching Skill generated with CLI-Anything. Linux/Blender compatibility remains to be verified.
- Use the same case with a wrong expected value to show that a zero exit status cannot confer verification. Rebuild and verify from a clean checkout.
- E2E exercises the native CLI and native Skill branch. Sand3D exercises the paired generation branch. Both launch fixtures must pass for V0.1. A native CLI without a compatible Skill is a subsequent acceptance case.
- Record baseline and AgentDock trial conditions, per-run elapsed time, manual interventions and verified results. Report first-time generation and clean recipe replay separately.

## Out of scope

Provider execution, catalog, OMA, a standalone builder daemon, optional Kit exports and broad app coverage are outside this iteration.
